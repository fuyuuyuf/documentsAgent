## 〇、先做这两件事

排查任何问题前，先跑这两条命令，能省掉大半时间：

```bash
# 1) 环境自检：依赖 / 离线素材 / API 配置，一次看清
python src/main.py --check

# 2) 带中间产物与详细日志运行
python src/main.py 你的论文.pdf --keep-debug -v
```

`--keep-debug` 会在 HTML 同级生成 `<报告名>.debug/` 目录：

| 文件 | 用来看什么 |
|---|---|
| `01_parsed.json` | 解析结果：页数、正文页、识别到的标题、被丢弃的页眉页脚、双栏页、各类统计与警告 |
| `02_analysis.json` | 模型的结构化输出：贡献、方法、论证、结论、局限、批判、术语 |
| `03_diagram.mmd` | 最终 Mermaid 源码（校验与修复后的版本） |
| `04_payload.json` | 送进前端看板的完整数据 |
| `05_body.txt` | 真正送进模型的正文全文（含 `## 标题` 标记） |

判断问题出在哪一环的快捷方法：

- `01_parsed.json` 里内容不对 → **PDF 解析**问题（见 C 节）
- `01` 对但 `02` 不对 → **大模型 / Prompt** 问题（见 A、B 节）
- `02` 对但 `03` / 看板不对 → **导图或前端**问题（见 D 节）
- 三样都对但命令跑不起来 → **环境**问题（见 E 节）

## A. 密钥与配置

### 1. 未配置 API Key

**现象**

```text
[fail] 缺少大模型配置，无法进行真实分析：
       · 未配置 API Key。请复制 .env.example 为 .env 并填写 LLM_API_KEY，或使用 `--mock` 离线演示模式。

解决办法（任选其一）：
  1) 复制 .env.example 为 .env，填入 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL；
  2) 先跑离线演示：python src/main.py 论文.pdf --mock
```

退出码为 `1`。程序在进入流水线**之前**就做了校验，因此不会产生任何 API 调用与费用。

**原因**

`Settings.validate()` 检测到 `LLM_API_KEY` 为空（同时也检查过 `OPENAI_API_KEY` 兜底）。常见具体情况：

1. 根本没创建 `.env` 文件；
2. 创建了 `.env`，但文件放在了错误的目录（必须在**项目根目录**，即与 `README.md` 同级，不是 `src/` 里）；
3. 文件名实际是 `.env.txt`（Windows 记事本另存为时最爱犯的错）；
4. `LLM_API_KEY=` 后面确实没填值，或只填了空格。

**解决**

```bash
# Windows PowerShell
Copy-Item .env.example .env
# macOS / Linux
cp .env.example .env
```

然后编辑 `.env`，至少填好这三行：

```dotenv
LLM_API_KEY=sk-你的真实密钥
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-v4-pro
```

验证：

```bash
python src/main.py --check
# 期望看到：API 配置: deepseek-chat @ https://api.deepseek.com/v1（key=sk-1...abcd）✓
```

如果暂时没有密钥，直接走离线演示模式（不需要 `.env`）：

```bash
python src/main.py 你的论文.pdf --mock
```

> 也可以不用 `.env`，直接设系统环境变量：
> PowerShell `$env:LLM_API_KEY="sk-xxx"`（仅当前窗口有效）
> CMD `set LLM_API_KEY=sk-xxx`
> macOS / Linux `export LLM_API_KEY=sk-xxx`
> 注意：`python-dotenv` 以 `override=False` 加载，**已存在的系统环境变量优先级更高** —— 如果你之前设过 `LLM_API_KEY`，改 `.env` 是不生效的，请先清掉系统变量。

### 2. HTTP 401：API Key 无效

**现象**

```text
[fail] 调用大模型失败：AuthenticationError: Error code: 401 - {'error': {'message': 'Authentication Fails...', 'type': 'authentication_error'}}（API Key 无效或已过期，请检查 .env 中的 LLM_API_KEY）
```

**原因**

请求确实发出去了，但服务端拒绝了这个密钥。按出现频率排序：

1. 密钥复制不完整（少几位、多了换行）；
2. 密钥前后带了空格、引号或中文标点 —— 例如写成 `LLM_API_KEY="sk-xxx"` 是**能**被正确剥离引号的，但写成 `LLM_API_KEY= sk-xxx` 或 `LLM_API_KEY='sk-xxx'`（中文引号）就未必；
3. 密钥已过期或被服务商吊销（多数平台在控制台重新生成后旧 key 立即失效）；
4. 密钥与 `LLM_BASE_URL` **不是同一家**服务商 —— 例如把 Kimi 的 key 配到 DeepSeek 的 Base URL 上，同样会返回 401；
5. 复制时把密钥中间的字符弄丢（从网页复制常带上不可见字符）。

**解决**

```bash
# 1) 先确认程序读到的到底是什么（--check 会脱敏打印）
python src/main.py --check
#    输出形如：API 配置: deepseek-chat @ https://api.deepseek.com/v1（key=sk-1...abcd）✓
#    看头 4 位和尾 4 位是否与你在控制台看到的密钥一致

# 2) 确认 .env 里没有行尾空格与中文引号
#    Windows
findstr /n "LLM_API_KEY" .env
#    macOS / Linux
grep -n "LLM_API_KEY" .env | cat -A
```

处理办法：

- 到服务商控制台**重新生成**一个密钥，用"复制"按钮复制，粘贴到 `.env` 时不要带引号；
- 确认密钥与 Base URL 属于同一家服务商；
- 确认没有残留的系统环境变量覆盖了 `.env`（见问题 1 末尾的提示）；
- 若密钥曾经提交到 Git 或截图外泄，**先吊销再重建**。

### 3. HTTP 404：模型名或 Base URL 错误

**现象**

```text
[fail] 调用大模型失败：NotFoundError: Error code: 404 - {'error': {'message': 'The model `deepseek-chat` does not exist'}}（Base URL 或模型名不正确，请检查 LLM_BASE_URL / LLM_MODEL）
```

或

```text
[fail] 调用大模型失败：NotFoundError: Error code: 404 - {'error': {'message': 'Not Found'}}（Base URL 或模型名不正确...）
```

**原因**

`404` 有两类完全不同的成因，需要区分：

| 报错里提到模型 | 成因 |
|---|---|
| `The model 'xxx' does not exist` / `model not found` | **`LLM_MODEL` 写错了**：拼写错误、大小写不符、用了别家的模型名、或该模型已下线 |
| 只说 `Not Found` / `page not found` | **`LLM_BASE_URL` 路径不对**：少了或多了路径后缀 |

各服务商的路径后缀**并不统一**，这是最容易踩的坑：

| 服务商 | 正确后缀 | 常见的错误写法 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/v1` | 漏掉 `/v1`；误用 `/v1/chat/completions`（多写了接口路径） |
| 月之暗面 Kimi | `https://api.moonshot.cn/v1` | 误用 `https://api.moonshot.cn` |
| 阿里云 DashScope 兼容模式 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 误用原生 DashScope 路径，或漏掉 `compatible-mode` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | 误写成 `/v1` |
| 本地 Ollama | `http://localhost:11434/v1` | 漏掉 `/v1` |

> 关键点：`LLM_BASE_URL` 只填到 **API 根路径**，不要带上 `/chat/completions`。程序（openai SDK）会自动拼接。
> 另外，程序在启动时会校验 `LLM_BASE_URL` 是否以 `http://` 或 `https://` 开头，格式明显不对会直接报 `LLM_BASE_URL 不是合法 URL：'...'`。

**解决**

```bash
# 1) 确认配置值
python src/main.py --check

# 2) 用最朴素的方式验证 Base URL 与模型名是否真的可用（把 <KEY> 换成你的密钥）
#    Linux / macOS
curl -s https://api.deepseek.com/v1/models -H "Authorization: Bearer <KEY>"
#    Windows PowerShell
Invoke-RestMethod -Uri "https://api.deepseek.com/v1/models" -Headers @{ Authorization = "Bearer <KEY>" }
```

`GET /models` 能列出该账号可用的模型 ID，直接照抄其中一个填进 `LLM_MODEL` 最稳妥。

- 确认路径后缀与服务商文档一致（尤其注意 `/v1`、`/v4`、`/compatible-mode/v1` 三种形态）；
- 确认模型名与服务商控制台的"模型列表"逐字符一致（区分大小写与连字符）；
- `.env.example` 第五节给出了五家服务商的可直接复制预设，但**它们是示例值，请以服务商最新官方文档为准**。

### 4. HTTP 429：触发限流

**现象**

```text
[warn] 调用大模型失败：RateLimitError: Error code: 429 - {'error': {'message': 'Rate limit reached for requests'}}（触发限流，请稍后重试或降低请求频率）
```

程序内部已经按 `2^n` 秒退避重试（最多 `LLM_MAX_RETRIES` 次），如果最终还是抛出，说明重试次数用完了。

**原因**

1. 短时间内连续跑了多次分析（例如批量处理论文、反复调试）；
2. 账号处于免费档 / 低档位，并发与速率配额很小；
3. 同一密钥在别处（IDE 插件、其他脚本）也在高频使用；
4. 论文过长导致单次请求 token 量过大，触发了 token 维度的限流而非请求数限流。

**解决**

```bash
# 1) 提高重试次数与间隔容忍度
#    在 .env 中把重试次数调大（下次运行生效）
LLM_MAX_RETRIES=4

# 2) 批量处理时主动降速（PowerShell 示例）
Get-ChildItem papers\*.pdf | ForEach-Object {
    python src/main.py $_.FullName -q
    Start-Sleep -Seconds 20
}
```

其他措施：

- 等 1–2 分钟再重试，多数平台的限流窗口是分钟级；
- 临时用 `--no-audience` 把两次调用减为一次，降低速率；
- 调小 `MAX_INPUT_CHARS`（如 30000）以减少单次 token 消耗；
- 若长期受限，升级账号档位或更换服务商；
- 调试阶段优先用 `--mock` / `--render-from`，避免反复消耗真实配额。

### 5. 余额不足 / 额度用尽

**现象**

```text
[fail] 调用大模型失败：APIStatusError: Error code: 402 - {'error': {'message': 'Insufficient Balance'}}（账户余额或额度不足）
```

不同服务商的表述不完全一样，程序会识别 `insufficient` / `balance` / `quota` 等关键字并给出中文提示，实际可能看到：

- `Insufficient Balance`
- `insufficient_quota` / `You exceeded your current quota`
- `Free tier is not available in your country` / `account is in arrears`

**原因**

账户余额为 0、免费额度已耗尽、或账号欠费被暂停。注意比赛明确说明：**调用 API 的测试费用需选手自行承担**。

**解决**

1. 登录服务商控制台查看余额与用量明细；
2. 充值或购买额度后重试；
3. 在排查阶段完全避开费用 —— 用离线演示模式验证链路：

```bash
python src/main.py 你的论文.pdf --mock
```

4. 想省钱地调前端，用已有分析结果重新渲染，**不产生任何 API 调用**：

```bash
python src/main.py 你的论文.pdf --render-from outputs/你的论文.dashboard.debug/02_analysis.json -o outputs/调试.html
```

5. 改用本地 Ollama（零 API 费用，但需要本机显存/内存，且小模型的 JSON 稳定性弱于云端）：

```dotenv
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:7b
LLM_API_KEY=ollama
```

6. 降低成本的其他手段：`--no-audience` 跳过第二轮调用；调小 `MAX_INPUT_CHARS`。

## B. 网络与请求

### 6. 请求超时

**现象**

```text
[fail] 调用大模型失败：APITimeoutError: Request timed out.（请求超时，可调大 LLM_TIMEOUT 或换用更快的模型）
```

或者进程长时间无输出、最后在 `[2/5] 调用大模型分析` 阶段失败。

**原因**

1. 论文很长（正文数万字符），单次请求的输入 token 量大，模型生成完整 JSON 需要较长时间；
2. `LLM_TIMEOUT` 默认 180 秒，对长论文 + 慢模型偏紧；
3. `LLM_MAX_TOKENS=8192` 偏大时，模型会倾向于生成更长的回复，耗时随之增加；
4. 服务商侧排队拥塞（高峰期尤其明显）；
5. 网络链路本身慢（跨境访问、代理不稳定）。

**解决**

```dotenv
# .env：把超时放宽到 5 分钟
LLM_TIMEOUT=300
```

其他措施：

- 用 `-v` 观察卡在哪个阶段，确认确实卡在 API 调用而非解析：

```bash
python src/main.py 你的论文.pdf -v
```

- 换更快的模型（小参数模型 / 服务商的"fast/turbo"档）；
- 调小 `MAX_INPUT_CHARS`（如 30000）缩短输入，直接减少耗时与费用；
- 服务商排队时稍后重试；必要时用 `LLM_MAX_RETRIES=3` 让程序自动多试几次（内部按 2/4/8 秒退避）；
- 如果是跨境网络问题，换用境内可直连的服务商（DeepSeek / Kimi / 通义 / GLM）。

### 7. 网络不可达

**现象**

```text
[fail] 调用大模型失败：APIConnectionError: Connection error.（网络不可达，请检查网络或 Base URL 是否可访问）
```

或更底层的 `getaddrinfo failed` / `SSLError` / `ProxyError` / `Connection refused`。

**原因**

1. 本机断网、Wi-Fi 未连接、或需要认证的校园网未登录；
2. 公司 / 学校防火墙拦截了 API 域名；
3. 系统配置了代理，但 `openai` SDK 未使用该代理（或代理本身不可用）；
4. 用本地 Ollama 时，Ollama 服务没有启动（`Connection refused`）；
5. `LLM_BASE_URL` 域名的 DNS 解析失败（域名拼错、或该域名被污染）。

**解决**

```bash
# 1) 先确认基础连通性
#    Windows PowerShell
Test-NetConnection api.deepseek.com -Port 443
#    macOS / Linux
curl -sS -o /dev/null -w "%{http_code}\n" https://api.deepseek.com/v1/models

# 2) 若在用本地 Ollama，确认服务在跑
ollama list
#    未启动则先执行：
ollama serve
#    再确认端口可达：
curl http://localhost:11434/v1/models
```

其他措施：

- 登录校园网 / 换网络（手机热点）再试；
- 若必须走代理，给终端设置代理环境变量后再运行：
  PowerShell `$env:HTTPS_PROXY="http://127.0.0.1:7890"`
  macOS / Linux `export HTTPS_PROXY=http://127.0.0.1:7890`
- 确认 `LLM_BASE_URL` 拼写正确（`https://` 而非 `http://`，域名无多余字符）；
- 用 `ping` / `nslookup` 确认域名能正常解析；
- 完全无法联网时，用 `--mock` 完成演示。

### 8. Windows 控制台中文乱码 / 日志报 UnicodeEncodeError

**现象**

控制台里中文变成 `??????` 或 `锟斤拷` 之类的乱码；或在极简终端里直接看到：

```text
UnicodeEncodeError: 'gbk' codec can't encode character '\u2713' in position ...
```

**原因**

Windows 控制台默认代码页是 GBK（cp936），无法表示 `✓`、`…`、`⚠` 等字符。程序已在 `main.py::_force_utf8_stdout()` 里把 `stdout`/`stderr` 重设为 UTF-8，并在 `Logger` 里对编码异常做了兜底，因此**主流程不会因为这个崩**；但若终端字体或代码页本身不支持，仍会显示乱码。

**解决**

```powershell
# 方案 1：临时把当前 PowerShell 切到 UTF-8（推荐，最简单）
chcp 65001
$OutputEncoding = [System.Text.Encoding]::UTF8

# 方案 2：Windows Terminal / PowerShell 7 默认就是 UTF-8，换用它
# 方案 3：把输出重定向到文件用 UTF-8 阅读器打开
python src/main.py 论文.pdf -v *> run.log
```

其他建议：

- 终端字体换成支持中文的等宽字体（如 `Cascadia Mono` / `Sarasa Mono SC`）；
- 在 CMD 里执行 `chcp 65001` 后再运行；
- 这类乱码**只影响控制台显示**，不影响生成的 HTML（HTML 始终以 UTF-8 写入并声明 `<meta charset="utf-8">`）。

## C. PDF 解析

### 9. PDF 是扫描件，没有文本层

**现象**

```text
[fail] PDF 中没有可提取的文本层（可能是纯扫描件）。请先用 OCR 工具（如 ocrmypdf）处理，或更换为文字版 PDF。
```

或解析侥幸通过，但日志给出警告、导图内容空洞：

```text
[warn] 正文仅提取到 320 字符，可能是扫描件或解析失败。
```

**原因**

扫描件本质是**每一页一张位图**，PDF 里根本没有文字对象，PyMuPDF 自然抽不出任何文本。程序宁可明确报错，也不拿空白内容去问大模型（那只会得到编造的答案）。

**解决**

```bash
# 1) 先确认是不是扫描件：看能不能选中并复制文字
#    用任意 PDF 阅读器打开，试着用鼠标选中一段正文
#    选不中 → 就是扫描件

# 2) 用 ocrmypdf 加文本层（需要先装 OCRmyPDF 与 Tesseract）
pip install ocrmypdf
#    Windows 还需安装 Tesseract-OCR 与 Ghostscript，详见 ocrmypdf 官方文档
ocrmypdf --language chi_sim+eng --deskew --clean input.pdf output_ocr.pdf

# 3) 用处理后的文件重新运行
python src/main.py output_ocr.pdf
```

其他可行路径：

- 用 Adobe Acrobat / 福昕等阅读器的"OCR 识别文本"功能处理后另存；
- 向论文来源索取文字版（arXiv、期刊官网、CNKI 下载的版本通常是文字版）；
- **混合型 PDF**（部分页是扫描图）也会触发报错 —— 请对整份文件统一 OCR 后再运行。

### 10. PDF 加密，打不开

**现象**

```text
[fail] 无法打开 PDF（可能已加密或文件损坏）：paper.pdf —— Failed to open document.
```

或者提示需要密码。退出码 `1`。

**原因**

PDF 设置了打开密码（user password）或权限密码（owner password，禁止复制/提取文本）。部分期刊下载的 PDF、以及从某些数据库导出的文件会出现这种情况。

**解决**

```bash
# 1) 判断是加密还是文件真的损坏
python -c "import pymupdf; d=pymupdf.open('paper.pdf'); print('encrypted:', d.is_encrypted, 'pages:', d.page_count)"

# 2) 若已知密码，可以直接解密（把 PASSWORD 换成真实密码）
python -c "import pymupdf; d=pymupdf.open('paper.pdf'); d.authenticate('PASSWORD'); d.save('paper_decrypted.pdf')"

# 3) 若无密码：用阅读器打开后「另存为」一份新 PDF，通常可去掉权限密码
```

其他措施：

- 有些 PDF 只设了**权限密码**（禁止复制），此时 `pymupdf` 往往仍能打开与提取 —— 如果报错，说明设的是打开密码；
- 文件损坏的情况：重新下载一次；用阅读器的"修复"功能另存；
- 用 `qpdf --decrypt in.pdf out.pdf` 也可处理（需另装 qpdf）。

### 11. 中文乱码 / 正文出现方块或问号

**现象**

生成的看板里中文标题、正文显示为 `□□□`、`?????`，或提示：

```text
[warn] 正文仅提取到 800 字符，可能是扫描件或解析失败。
```

提取出的内容里夹杂大量无意义符号。

**原因**

1. **PDF 内嵌字体缺少 ToUnicode 映射表** —— 这是最常见的原因。PDF 里的字符以字形 ID 存储，没有 ToUnicode 表时无法反查回 Unicode，抽出来就是乱码；
2. **控制台显示乱码但文件内容正常** —— 这是显示问题，不是数据问题（见问题 8）；
3. 早期国产排版软件生成的 PDF 使用了非标准编码；
4. 生成的 HTML 本身没问题，但用**非 UTF-8 编码的编辑器**打开时显示异常。

**解决**

```bash
# 1) 关键判断：乱码是在文件里，还是在终端里？
python src/main.py 论文.pdf --keep-debug
#    然后用 VS Code / Notepad++ 以 UTF-8 打开 outputs/xxx.debug/05_body.txt

# 2) 若 05_body.txt 里正文正常 → 是终端显示问题，按问题 8 处理
# 3) 若 05_body.txt 里也是乱码 → 是 PDF 字体映射问题
```

针对字体映射问题：

- 用 OCR 重新生成文本层（即使是文字版 PDF，OCR 也能重建可读文本）：

```bash
ocrmypdf --language chi_sim+eng --force-ocr input.pdf output.pdf
```

- 换用其他 PDF 来源（出版社官网、arXiv、CNKI 等版本编码通常更规范）；
- 用阅读器的"导出为文本"功能另存后核对；
- 检查是不是**控制台乱码**导致的误判 —— 生成的 HTML 始终以 UTF-8 写入，并在 `<head>` 声明 `<meta charset="utf-8">`。

若怀疑 HTML 被改坏，用 `--keep-debug` 对比 `04_payload.json`（UTF-8 JSON）里的中文是否正常。

### 12. 双栏论文阅读顺序错乱

**现象**

日志给出警告：

```text
[warn] 5/8 页疑似双栏排版，已按块排序重组，建议人工抽查阅读顺序。
```

导图内容里出现语义断裂的引用：句子被从中间切断、左栏的后半句和右栏的前半句拼在一起，引用定位到的 `evidence` 读起来不连贯。

**原因**

PDF 不存储"阅读顺序"，只存储文本块坐标。双栏排版下，同一水平线上的左右两个块在坐标上属于同一 `y` 区间，若排序策略不当就会左一句右一句地交错。程序的做法是：检测到双栏（左右半区各有 ≥3 个成规模文本块，且跨越中线的块占比 ≤20%）后，按 `(top, x0)` 重排 —— 这对**规整的双栏**有效，但对下列结构仍可能出错：

1. **跨栏大标题 / 跨栏图表**：一个块横跨左右栏，会打断栏内顺序；
2. **左右栏起始高度不同**（左栏有图，右栏提前开始）；
3. **三栏排版**（程序只按左右两半做二分检测）；
4. **栏内嵌套图表 + 通栏脚注**。

**解决**

程序已经把这个风险显式转成警告，而不是静默产出。处理方式：

```bash
# 1) 量化确认：看有多少页被判为双栏
python src/main.py 论文.pdf --keep-debug
#    打开 01_parsed.json，看 "two_column_pages" 与 "stats"
```

2. 人工抽查：打开看板，重点看「方法路径」「实验与证据」两个分区的内容是否连贯；
3. 若乱序严重，改用**单栏重排版**的版本再跑 —— 用阅读器的"重新排版"、或先用工具转成单栏 PDF；
4. 检查 `01_parsed.json` 里的 `headings` 列表是否漏掉了跨栏标题（标题识别依赖字号与编号，跨栏标题通常识别正常）；
5. 若确认是解析器疏漏，可在 `src/parse.py` 的 `_detect_two_column()` 中放宽 `spanning` 块的容忍比例。

> 提示：`two_column_pages` 与页码列表会一并写进看板的 payload（`meta.twoColumnPages`），页面上可以直接看到哪些页被判为多栏。

### 13. 长论文被节选

**现象**

```text
[warn] 正文 92000 字符，超过模型输入上限 60000，超出部分将按页节选（可调大 MAX_INPUT_CHARS）。
[warn] 正文较长，已按页节选为约 60000 字符；重要结论仍需核对原文
```

看板内容覆盖各页的节选，但每页中间的细节可能缺失。正文里会出现省略标记：

```text
[本页仅展示节选，部分内容省略]
```

**原因**

`MAX_INPUT_CHARS` 默认 60000 字符。超出时系统会按页分配字符预算，优先保留页首和页末，并在 Prompt 中明确提醒模型只依据可见内容分析。它仍是节选，不等同于完整的分块汇总。

**解决**

```dotenv
# .env：先确认你的模型上下文窗口，再把上限调到安全范围内
# 经验换算：中文约 1 字符 ≈ 0.7 token，60000 字符 ≈ 40000+ token
MAX_INPUT_CHARS=120000
```

选择方案：

| 方案 | 做法 | 适用 |
|---|---|---|
| 调大上限 | `MAX_INPUT_CHARS=120000` | 模型上下文 ≥128K（如 Kimi、qwen-long） |
| 换长上下文模型 | 改 `LLM_MODEL` / `LLM_BASE_URL` | 论文 30 页以上 |
| 接受节选 | 保持默认，人工核对缺失部分 | 只需把握主干逻辑 |
| 拆分处理 | 把论文按章节拆成多个 PDF 分别运行 | 超长综述类论文 |

注意：调大 `MAX_INPUT_CHARS` 会同时**增加费用与耗时**，且 `LLM_MAX_TOKENS` 也要留足（结构化 JSON 本身不短）。若模型上下文不够而硬调大，服务端可能直接返回 400/413 错误。

### 14. 参考文献被误当作正文

**现象**

导图里出现大量与论文主旨无关的节点，内容是作者名 / 期刊名 / 年份，或术语解读里混进了一堆参考文献标题；`evidence` 引用的都是 `[12] Smith et al., 2020` 这样的条目。

**原因**

程序在 `_assemble()` 里对正文装配做了两件事：

1. **遇到 `references` / `参考文献` / `acknowledgments` / `致谢` / `appendix` / `附录` 章节标题即停止装配正文** —— 之后的页不再进入正文；
2. 页眉页脚按"跨页重复"启发式删除。

因此正常情况下参考文献不会进入正文。若仍然出现，通常是因为：

1. **标题没被识别成标题**：参考文献标题字号与正文相同、没编号，导致 `_classify_heading()` 没判出来 → 停止规则没触发；
2. **中英混排标题**：写成 `REFERENCES AND NOTES`、`参考文献（References）` 这类变体，不在内置标题词表中；
3. **参考文献出现在正文中段**（部分期刊把 Related Work 的引用列表放在正文中间）；
4. **正文页里含着长引用块**（如综述论文的文献综述段落本身就在讨论某篇文献）。

**解决**

```bash
# 1) 先确认解析结果里到底有没有参考文献
python src/main.py 论文.pdf --keep-debug
#    打开 01_parsed.json：
#      · headings 列表里有没有 "References" / "参考文献"
#      · body_pages 覆盖到第几页（若覆盖到最后一页，说明停止规则没生效）
#    打开 05_body.txt 末尾，看是否混入了文献条目
```

2. 若确认没识别到参考文献标题，可在 `src/parse.py` 的 `_CANONICAL_HEADINGS` 与 `_STOP_SECTIONS` 中补充该论文实际使用的标题写法（如 `references and notes`、`bibliography`、`文献`）；
3. 若章节标题**没有编号也不是标准词**，可以通过字形判别（通常参考文献字号略小）—— 属于需要按论文调整的启发式规则；
4. Prompt 中已明确写了"论文的参考文献（References / 参考文献）部分不属于正文，不要为其生成节点"，因此**即使少量文献内容混入正文，模型通常也不会为它们建节点**；若模型仍生成了文献节点，可调 `MAX_INPUT_CHARS` 缩小正文范围以避开文献区。

### 15. 导图渲染失败或空白页

**现象**

打开 HTML 后，导图区域只显示一个加载提示或一片空白：

```text
正在渲染导图…
```

或者显示错误信息 + 一大段 Mermaid 源码 + 节点列表（这是**兜底视图**，说明程序已经预判到渲染可能失败并做了保护）。

命令行侧可能伴随：

```text
[warn] 预校验未通过：第 12 行：[ 与 ] 数量不匹配（1 vs 2）。
[  ok ] 规则化修复成功：补全未闭合的 subgraph、统一边语法与缩进
[fail] Mermaid 语法仍存在问题，看板已启用兜底视图（节点列表 + 源码）
```

**原因**

按可能性排序：

1. **Mermaid 语法确实有问题**：本作品把 Mermaid 生成限制在本地确定性代码里并做了 `validate_mermaid()` 预校验，但仍可能出现三类问题 —— 标签内容异常、节点数量过多（>60 会给出提示）、`subgraph` 层级异常。程序的三级兜底是：预校验 → `repair_mermaid()` 规则修复 → 大模型修复一次；
2. **浏览器过旧**：`mermaid.min.js` 需要现代浏览器；IE 与旧版 Edge 无法渲染；
3. **`mermaid.min.js` 缺失或被替换**：程序在渲染前会检查 `assets/vendor/mermaid.min.js`，缺失时直接报 `缺少离线渲染资源` 并提示 `python tools/fetch_mermaid.py`；但如果你手工换成了不兼容的版本，可能运行时才报错；
4. **HTML 文件被截断**：拷贝过程中断、或编辑器打开后又保存导致内容损坏；
5. **节点确实一个都没生成**：分析结果为空时 `build_diagram()` 会给出警告 `分析结果为空，未能生成任何节点。`

**解决**

```bash
# 1) 看 Mermaid 源码，确认问题在不在代码本身
python src/main.py 论文.pdf --keep-debug
#    打开 outputs/xxx.debug/03_diagram.mmd
#    把它粘贴到 https://mermaid.live 在线编辑器验证（这一步需要联网，仅用于排查）

# 2) 在本机做纯 Python 静态校验（不依赖 Node / mermaid-cli）
python -c "from src.diagram import validate_mermaid; import pathlib; r=validate_mermaid(pathlib.Path('outputs/xxx.debug/03_diagram.mmd').read_text(encoding='utf-8')); print(r.summary()); [print(' -',e) for e in r.errors]"

# 3) 直接尝试规则修复并打印修复动作
python -c "from src.diagram import validate_mermaid, repair_mermaid; import pathlib; code=pathlib.Path('outputs/xxx.debug/03_diagram.mmd').read_text(encoding='utf-8'); fixed,acts=repair_mermaid(code); print('修复动作:',acts); print(validate_mermaid(fixed).summary())"
```

其他处理：

- 换用 Chrome / Edge / Firefox 的最新版本打开；
- 确认 `assets/vendor/mermaid.min.js` 存在且大小约 3.3 MB；缺失时执行 `python tools/fetch_mermaid.py`；
- 重新生成一次 HTML，确认文件大小在 3 MB 以上（明显偏小说明被截断）；
- 看板内置了兜底视图：即使 Mermaid 渲染失败，也会显示错误信息、Mermaid 原始源码和完整节点列表 —— 内容不会丢，可以到「🧾 Mermaid 源码」标签页复制源码去别处渲染。

### 16. 生成的 HTML 打开后是白屏

**现象**

双击 HTML 后浏览器一片纯白，没有任何内容，控制台（F12）里可能报 JS 错误。

**原因**

与问题 15 的"导图空白"不同，**整页白屏**说明 HTML 结构或脚本注入出了问题：

1. **`assets/templates/app.js` 缺失**：`render.py::load_assets()` 会在渲染前检查并抛 `缺少前端脚本：.../app.js`。如果你拿到的是不完整的仓库，会先在这里失败；
2. **数据里的 `</script>` 提前闭合了脚本标签**：程序已把 payload JSON 中的 `<` `>` `&` 转义为 `\u003c` / `\u003e` / `\u0026`，并把 JS 内部的 `</script` 切断为 `<\/script`。若你手工改过 `render.py` 或 `dashboard.html`，这条保护可能失效；
3. **文件名/路径问题**：放在中文路径或超长路径下，个别浏览器加载异常（少见）；
4. **浏览器过旧**：前端使用可选链（`?.`）等 ES2020 语法；
5. **文件不完整**：拷贝/传输中断导致 HTML 尾部缺失。

**解决**

```bash
# 1) 打开浏览器开发者工具（F12）→ Console，看第一条红色报错
#    常见线索：
#      "Uncaught SyntaxError: Unexpected token '<'"  → 脚本被 HTML 内容提前闭合
#      "Cannot read properties of null"              → payload 元素没找到
#      "mermaid is not defined"                      → mermaid.min.js 没内联成功

# 2) 确认产物完整性：检查三个关键片段是否存在
#    Windows PowerShell
Select-String -Path outputs\xxx.dashboard.html -Pattern 'id="payload"','mermaid','<div class="topbar"' | Select-Object -First 10
#    macOS / Linux
grep -c 'id="payload"' outputs/xxx.dashboard.html

# 3) 确认文件大小（正常 3–4 MB；明显偏小说明被截断）
Get-Item outputs\xxx.dashboard.html | Select-Object Name, Length
```

其他处理：

- 重新生成一次，别手工编辑产物 HTML；
- 从完整仓库补齐 `assets/templates/app.js` 与 `assets/vendor/mermaid.min.js`；
- 换 Chrome / Edge 最新版打开；
- 把文件挪到纯英文短路径（如 `D:\out\a.html`）再试。

### 17. Mermaid 语法报错

**现象**

命令行侧：

```text
[warn] 预校验未通过：第 23 行：引号未闭合。
[warn] 规则化修复不足，尝试让大模型二次修复
[  ok ] 大模型修复成功
```

或 Mermaid 渲染时报形如 `Parse error on line 23: ... Expecting 'SQE', got 'PS'` 的错误。

**原因**

即使 Mermaid 由本地代码拼装，语法风险仍来自**标签内容**（标签文本来自模型输出的论文内容）。程序已经做了两层防护：

1. `sanitize_label()` 主动清洗危险字符：把 `"` → `'`、`(` → `（`、`)` → `）`、`[` → `【`、`]` → `】`、`{` → `｛`、`}` → `｝`、`|` → `/`、`;` → `；`、`#` → `＃`、`&` → `和`、`<` → `＜`、`>` → `＞`、`\` → `/`，并按中英文分别智能截断（中文按字符数并在标点处断开，英文按词截断），最后用双引号整体包裹；
2. `validate_mermaid()` 在写文件前静态校验：首行类型合法、`subgraph` 成对闭合、括号与引号配平（忽略引号内内容）、节点 id 合法、边端点已定义、标签非空。

仍可能触发语法错误的情况：

1. 模型在标签里塞进了**罕见 Unicode 字符**（emoji、数学符号、零宽字符）；
2. 人工编辑过 `03_diagram.mmd` 并注入到看板；
3. 节点总数过多（>60 时给出拥挤提示）；
4. `mermaid.min.js` 版本与生成的语法特性不完全匹配。

**解决**

```bash
# 1) 定位到具体行与原因
python -c "from src.diagram import validate_mermaid; import pathlib; r=validate_mermaid(pathlib.Path('outputs/xxx.debug/03_diagram.mmd').read_text(encoding='utf-8')); print('\n'.join(r.errors) or '无错误'); print('---'); print('\n'.join(r.warnings) or '无警告')"

# 2) 跑一次规则修复，看能不能救回来
python -c "from src.diagram import validate_mermaid, repair_mermaid; import pathlib; p=pathlib.Path('outputs/xxx.debug/03_diagram.mmd'); code=p.read_text(encoding='utf-8'); fixed,acts=repair_mermaid(code); print('动作:',acts); print(validate_mermaid(fixed).summary())"
```

`repair_mermaid()` 会做这些事：移除代码围栏、补写缺失的 `flowchart TD` 首行、删除首行之前的解释文字、统一边语法（`--->`/`-->` 规范化并加空格）、补全未闭合的 `subgraph`、统一缩进。

其他措施：

- 正常流程下**不需要手工干预**：预校验失败会自动触发规则修复，再失败会自动让大模型修一次，产物必须再次通过本地校验才被采纳；
- 若标签里出现异常字符，可以在 `src/diagram.py` 的 `_CHAR_REPLACEMENTS` 中补充映射；
- 如果是你手工改过 `.mmd`，请改回由 `build_diagram()` 生成，或把修改同步进代码；
- 用 `python tools/fetch_mermaid.py` 重新获取官方版本的 `mermaid.min.js`，避免版本错配。

## E. 环境与版本

### 18. Python / Node 版本不匹配

**现象**

Python 版本过低：

```text
SyntaxError: invalid syntax
  File "src/config.py", line 76
    api_key: str = ""
```

或

```text
TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'
```

依赖版本过低：

```text
ImportError: cannot import name 'pymupdf' from partially initialized module
ModuleNotFoundError: No module named 'openai'
```

Node 相关（一般不会遇到，但可能被误引）：

```text
'mermaid' is not recognized as an internal or external command
```

**原因**

1. **Python < 3.10**：代码使用 PEP 604 联合类型（`str | None`）、`list[str]` 内建泛型等 3.10+ 语法。在 3.9 及以下会直接语法错误；
2. **装到了错误的 Python 环境**：系统里有多个 Python（如 Microsoft Store 版 + 官网安装版 + conda），`pip` 与 `python` 指向不同的解释器，依赖装到了另一个环境；
3. **虚拟环境没激活**就装了依赖，或激活后又开了新终端；
4. **依赖版本过旧**：`pymupdf` < 1.24 只有 `fitz` 旧包名（代码已做兼容回退 `import fitz as pymupdf`），但过老的版本仍可能缺少用到的 API；`openai` < 1.30 没有 `OpenAI` 客户端类与 `base_url` 参数；
5. **Node.js 问题**：本作品**不需要 Node.js** —— Mermaid 校验用纯 Python 正则实现，前端渲染在浏览器里完成。若看到 mermaid-cli 相关报错，说明你在手工执行额外命令，那不在本项目的运行路径上。

**解决**

```bash
# 1) 确认当前解释器版本与路径（必须是 3.10+，开发环境为 3.14）
python --version
python -c "import sys; print(sys.executable)"

# 2) 确认 pip 与 python 是同一个环境
python -m pip --version
python -m pip install -r requirements.txt   # 始终用 python -m pip，避免指向错误的 pip

# 3) 一键自检依赖与素材
python src/main.py --check
```

推荐做法（彻底避免多环境问题）：

```bash
# 重建一个干净的虚拟环境
python -m venv .venv
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
# macOS / Linux
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python src/main.py --check
```

其他措施：

- 升级 Python 到 **3.10 或更高**（推荐 3.11–3.14）；Python 3.13+ 已移除标准库 `cgi` 模块，本项目网页上传功能改用 `email` 解析 multipart，因此**不受影响**；
- `pymupdf` 装不上时，确认 Python 版本有对应的 wheel（新版本发布初期可能滞后），或临时升/降 Python 小版本；
- `python-dotenv` 缺失**不阻塞**运行：`src/config.py` 会退化为内置的极简 `.env` 解析器（支持 `KEY=VALUE`、`#` 注释、引号剥离），只是功能略弱；
- 不要为了本项目去装 `mermaid-cli` 或 Node.js —— 那是额外依赖，与"产物离线可用"的设计目标相悖。
